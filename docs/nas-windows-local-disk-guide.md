# 把 NAS 挂成 Windows 本地磁盘：三种方案的实测对比与五个踩坑清单

> 利益披露：作者所在团队维护文末提到的 ScsDrive，与该产品存在利益关系。文中所有结论都来自我本人在 Windows 11 + 群晖 DS920+ 上的实测，仅代表我的环境。

## 一、先说结论

只想偶尔把 NAS 上的文件拷到本地，Windows 自带的 WebDAV 映射就够了；如果需求里包含「开机自动挂载」「网线切换后自动恢复」「大文件传输不中断」，原生映射基本撑不住。我把这三条列成硬指标，逐项实测。

## 二、方案一：Windows 原生 WebDAV 映射

资源管理器右键「映射网络驱动器」，填 https 地址，勾选「使用其他凭据」。零安装是它最大的优点。实测三个硬伤：

1. 单文件超过 4GB 时，传输中断后重连经常从头再来，进度条回到零；
2. 带中文名或含 `# & ?` 的文件名同步异常，偶发创建出乱码文件；
3. 系统凭据管理器会把 WebDAV 密码留在用户配置里，多人共用机器时风险不小。

## 三、方案二：通用第三方客户端

RaiDrive、Cyberduck 这类图形客户端，稳定性和断点续传明显好于原生映射，代价是常驻后台、免费版有连接数或流量限制。对自动化没有需求的话，这是我最推荐给普通用户的选项。

## 四、方案三：自建挂载（开机自启 + 崩溃重连）

我用 rclone 加 WinFsp 组合，再加一个负责健康检查的守护进程，掉线时按 10s、30s、60s 退避重连。这套方案的收益集中在三点：

- 缓存目录放 SSD，热点小文件走本地缓存，NAS 断网时已缓存文件仍可读；
- 退出后重启不丢盘符，重连后目录树自动重建；
- 传输日志可回溯，方便区分「NAS 慢」和「网络抖动」。

## 五、五个真实踩过的坑

1. **大文件写入中断** —— 不是协议问题，是 WebDAV 服务端对单次 PUT 大小有限制。解法是分块上传并在客户端做断点记录。
2. **盘符消失** —— 网络适配器重新枚举后原有映射会掉，必须有重建逻辑，而不是只依赖开机自启。
3. **中文文件名乱码** —— 服务端编码与客户端不一致，建议先在 NAS 端统一编码，客户端做一次批量重命名。
4. **时间戳不同步** —— 跨设备访问时本地时间被刷新，脚本依赖 mtime 判断新旧会出错，建议改用内容哈希。
5. **权限迷宫** —— NAS 上是 POSIX 权限，客户端映射成 Windows ACL 时常出现「能看到目录但打不开文件」，得在服务端统一用一套 UID/GID。

## 六、什么时候值得上自建方案

如果诉求只是「像本地盘一样打开 NAS」，通用客户端足够，别过度设计。只有当开机自启、状态可观测、崩溃后自动恢复变成刚需时，自建方案才划算。

我把这套自建挂载做成了可安装的 Windows 客户端 ScsDrive，页面在这里：https://drive.scsoi.com
